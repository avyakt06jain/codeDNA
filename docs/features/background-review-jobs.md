# Observable background review jobs

**Status:** Verified, updated 2026-10-29.

## Contract

`POST /api/prs/{pr_id}/review-jobs` and `POST /api/prs/{pr_id}/comparison` validate the stored PR and atomically claim work. SQLite uses `BEGIN IMMEDIATE` before the active-job check; other SQL dialects lock the stored PR row. If a queued/running job already exists for that PR and kind, the response returns its ID and `reused: true` without scheduling another task. Otherwise the API persists one queued job, returns `reused: false`, and schedules execution after the response. Clients poll `GET /api/review-jobs/{job_id}`.

The frontend keeps `reused` as part of its typed creation result. When true, Review Workspace or Memory Lab immediately renders and politely announces that it reattached to existing work and did not start another provider call/branch. Normal stage polling then continues against the returned job ID.

Creation responses have a separate 10-second browser bound. Because aborting the browser request does not prove the backend stopped, timeout never replays the POST. The client instead checks the same PR/kind active claim three times through GET. A discovered claim is returned as `reused` work, stored, and polled normally. If no claim is visible, a dedicated uncertainty error clears the exact-PR readiness marker and disables another creation attempt; absence is not mislabeled as confirmed creation failure.

That state exposes `Check creation status`. The action performs the existing bounded active lookup and, only when no active claim exists, latest-result lookup for the exact PR and kind. A visible claim is saved and polled with the reattachment announcement, a completed result is restored, and a successful empty boundary permits a new explicit request protected by the backend's atomic claim. A read error leaves creation disabled and recreates the action. The manual result focuses the restored result, named workspace, or check action. It never sends a creation POST.

Stages are `queued`, `starting_hindsight`, `recalling_and_reviewing`, `reviewing_diff`, `reviewing_baseline`, `complete`, and `failed`. Single-review completion embeds one persisted serialized `ReviewRun`; the frontend requires its normalized run ID to pass the bounded correlation grammar, its `pr_id` to equal the PR supplied by the current operation, its raw status to equal `complete`, its raw mode to explicitly equal `memory` or `baseline`, and its provider/model identity to be non-blank before accepting terminal success. Provider is trimmed and bounded to 80 characters; model is trimmed and bounded to 160 characters, matching their persisted columns. Latest and known-mode job operations also require mode equality with the request; rediscovered active work without a stored client mode still must declare a valid mode. Invalid/defaulted identity or state produces a terminal integrity error, clears the active locator, and triggers neither latest-result fallback nor replacement POST. Latest-review recovery enforces the same state/context boundary without starting work. Comparison completion embeds persisted memory/baseline runs and deterministic evaluation; both nested runs must carry valid bounded IDs, explicitly declare their expected memory/baseline modes, report `status: complete`, carry equal non-empty PR/provider/model identities, and match the PR identity supplied by the current start/poll/recovery operation before the result is accepted. A partial, failed, missing, context-mismatched, or mutually identity-mismatched branch is rejected as correlation-invalid. The evaluation must also carry both matching run IDs, all six backend-defined Boolean guardrails, all seven backend-defined numeric counts, and a Boolean overall outcome; `same_candidate` and `same_model` must be true and independently supported by the branch fields. Counts must be finite non-negative integers equal to values recomputed from the normalized nested results. The remaining four guardrails must likewise equal content-derived checks for non-empty validated memory evidence, fully resolved team-policy citations, and absent baseline citations/team-policy findings. A partial/non-Boolean required set, invalid/mismatched count or content check, missing outcome, or missing/mismatched evaluation run ID is rejected. That outcome must equal the conjunction of the normalized guardrail checks. A present but rejected comparison produces a correlation-integrity terminal error, distinct from a missing payload; both clear the locator without replay. Unexpected exceptions expose only `review_service_unavailable`; known application validation errors use bounded error codes.

Single-review completion additionally requires an explicit findings array containing only object entries. Missing/non-array collections and malformed entries are correlation-invalid instead of silently becoming an empty review; an explicit empty array is accepted. Every finding must then satisfy the backend's required text bounds, nullable line rule, category/severity/confidence enums, optional-suggestion bound, and evidence-list shape before frontend normalization. Team-convention findings require evidence, while general findings must remain uncited. Every team citation must match a non-blank decision ID in same-result validated retrieval evidence. Completed elapsed time is mandatory and must be a finite non-negative integer.

Cited validated evidence requires complete fact/document/decision/source-PR/repository/bank identity and a positive source PR number before it can ground single-review output. Every cited record must satisfy that shape, cited records must agree on repository ID, repository slug, and bank ID, and their repository ID/slug must match Review Workspace's route and selected API-catalog entry. Recovery waits for repository catalog resolution. Chunk ID remains nullable under the backend contract.

Review Workspace does not begin saved-job polling, active discovery, or latest-result recovery until the fetched pull request's ID and repository ID match the route. Off-route PR payloads cannot use a valid-looking job locator to recover or render state in another repository context.

Before the same recovery boundary, the full PR must carry safe bounded identities, a positive integer number, bounded title/description strings, a diff within 100,000 UTF-8 bytes, and an optional parseable creation timestamp. Its unified diff must also satisfy text-only/file-count/path/header/hunk/count/addition rules. Malformed metadata or grammar cannot unlock a saved locator or active/latest read.

Repository catalog identity is validated before that boundary: malformed rows, unsafe/blank IDs or slugs, blank display names, duplicate IDs, and duplicate slugs reject the complete catalog. A rejected catalog cannot start PR or review-recovery reads.

Memory Lab applies a repository-scoped PR-catalog boundary before selecting a candidate: malformed rows, invalid IDs/numbers/titles/timestamps, duplicate IDs, and duplicate numbers reject the whole list. Existing selection/recovered comparison state is cleared before the read, so a failed catalog cannot start saved/status/active/latest recovery.

The browser maps stages to readable loading text and stops after six minutes. Creation, active-discovery, and job-status responses include only UTC `created_at` and `updated_at` job timestamps alongside the existing sanitized state. The client accepts only parseable timestamp strings, normalizes them to ISO UTC, and updates the diagnostic values after every successful poll. After a creation response, it stores the validated opaque job ID in per-tab session storage under the job kind and PR ID. A refresh resumes polling that same job through `GET`; it does not repeat the creation `POST`. Success and known terminal failure clear the locator, while unmount, timeout, and transient request errors preserve it for later recovery. The original synchronous review route remains for smoke/compatibility use, while Review Workspace uses jobs.

Queue responses repeat authoritative `pr_id` and `kind`. Before saving a locator, the client requires exact request correlation, a bounded job ID, a Boolean `reused` value, queued/running status, a safe bounded stage, and chronological parseable timestamps. Rejection does not prove the POST failed, so the browser performs the existing bounded exact-PR/kind active-claim GET reconciliation. Only a separately validated claim may be persisted and polled; the response's untrusted ID is ignored and no replacement POST is issued.

Every status response repeats job, PR, and kind identity and is validated before progress callbacks or result handling. It must match the requested operation, use a persisted status and safe stage, contain chronological timestamps, omit an error outside failure, and pair terminal status with the corresponding terminal stage. Successive accepted polls must keep `created_at` unchanged, never decrease `updated_at`, never move from running/terminal state back toward queued, and use a strictly later update time whenever status or stage changes. Failed state additionally requires a bounded machine-safe error code. An invalid or regressed envelope is terminal: its nested review/comparison is ignored, the saved locator is cleared, and neither latest-result fallback nor creation is attempted.

When per-tab storage has no locator, the page calls `GET /api/prs/{pr_id}/review-jobs/active?kind=review|comparison`. The backend verifies the PR exists and selects only the newest queued/running job for that exact PR and kind. The client requires exact PR/kind correlation. A present job also requires a valid opaque ID, queued/running status, safe stage, and chronological timestamps; an absent job requires explicit null job/status/stage/timestamps. A malformed, partial, cross-request, or terminal response fails recovery before storage, individual polling, or latest-result fallback. Only a valid empty response permits the latest completed-result read.

While a job is active or recoverable, both pages render a collapsed `Active job details` disclosure. It contains only the already validated opaque job ID, a controlled human-readable status label, and started/updated ages with exact local times. Completion or known terminal failure removes it. Provider request/response bodies, prompts, credentials, recalled text, and raw errors are never placed in this disclosure.

If a parseable persisted `updated_at` remains unchanged for three minutes, a warning appears outside the collapsed disclosure and is exposed as a status message. It says only that the job has not reported progress; it does not label the worker failed or stuck. CodeDNA continues polling the same job ID and does not create a retry, replacement job, or provider call. A blocking provider operation can legitimately cross the threshold, so the warning is diagnostic rather than terminal.

Each status GET independently classifies retryable failures. Status, active-discovery, latest-result, and repository active-summary reads abort after 10 seconds. Status timeout, network errors, and HTTP `408`, `425`, `429`, `500`, `502`, `503`, and `504` receive at most three consecutive retries after 1, 2, and 4 seconds. The page announces a review- or comparison-specific reconnecting state during backoff. A successful GET resets the counter; non-retryable responses and the fourth consecutive transient failure surface without another automatic request. Initial active/latest timeout becomes the existing actionable saved-recovery failure, while repository-summary timeout uses its existing bounded read-only recovery. After polling exhaustion, an explicit `Check review again` or `Check comparison again` action starts another status loop for the preserved opaque job ID. Automatic and manual retries are GET-only and never create or replay provider work. Creation uses its separate timeout only with the claim-reconciliation/fail-closed behavior above.

An HTTP `404` has separate terminal meaning: the saved active-job locator no longer resolves. The page clears that locator, queries the existing latest-completed endpoint for the same PR, and restores the persisted result if present. When no completed result exists, it asks for a new explicit run. Neither branch sends a job-creation POST.

## Trust and reliability boundaries

- Repository and PR identity still come from application storage.
- Workers open an independent SQLAlchemy session; request sessions are never reused across threads.
- Job state and completed results survive browser reloads.
- The session-stored job ID is a recovery locator, not an authorization decision; repository/PR ownership and work execution remain backend controlled.
- Closing a tab discards its local locator, but a new tab discovers same-PR active work from SQLite. Simultaneous creation requests serialize and reuse the same active job instead of duplicating provider work.
- The repository overview uses a read-only repository-scoped lookup and lists queued/running jobs with their owning PR, kind, stage, and sanitized timestamps. While rows remain it refreshes only this summary every five seconds, stopping on an empty response, error, repository change, or unmount. It does not poll individual job results or create provider work.
- That repository summary is fail closed as a collection. Each backend row repeats its PR-derived repository ID; the client requires exact route correlation, valid bounded job/PR/title/stage identity, a positive integer PR number, queued/running state, and chronological parseable timestamps. Job IDs and PR-kind claims are unique, repeated PR references agree on number/title, and different PR IDs cannot share a number. Any violation rejects every row and uses the existing summary-only recovery path without an individual status read or provider call.
- A persistent polite/atomic live region announces a nonempty-to-empty overview transition exactly once, conservatively saying only that work is no longer running and directing the user to inspect the saved result or failure. Initial empty state and repository navigation remain silent.
- Overview summary reads reuse the frontend's transient classification: network errors and HTTP `408`, `425`, `429`, `500`, `502`, `503`, and `504` retry after 1, 2, and 4 seconds. Existing rows remain visible while reconnecting; success resets the counter, and exhaustion or a nonretryable response stops the summary loop with an explicit error.
- After that loop stops, `Check active work again` starts a fresh bounded cycle against the same repository summary. It does not call an individual job endpoint, submit a review/comparison, or invoke a provider.
- Because the retry button disappears during recovery, focus moves deterministically after resolution: to Active work when rows return, to the overview heading when the result is empty, or to the recreated retry action after another terminal failure.
- Every successful repository active-summary response records a client-side `Last checked` instant. Active work renders it as a localized, machine-readable `<time>`; transient failures do not advance the value.
- A successful empty response renders `No active work` with the same check instant and explicit queued/running review/comparison scope. It does not claim that a provider was contacted.
- `Check for active work` starts a summary-only bounded cycle from that empty state. If another tab queued work, the panel changes to Active work, focus moves to its heading, and ordinary read-only monitoring resumes without a creation POST.
- Repository summary timers pause while `document.visibilityState` is hidden. Initial and scheduled reads wait; returning to visible triggers one immediate summary check, and component cleanup removes both timers and the visibility listener. Exhausted/nonretryable errors remain stopped across visibility changes until the explicit retry action.
- Active work does not resume after API-process termination because the local MVP uses in-process FastAPI background tasks, not an external worker queue.
- The shared Hindsight server is API-owned, while each worker creates its own SDK client to avoid sharing event-loop-bound client state across threads.
- The next API startup atomically marks every leftover `queued`/`running` job `failed` with `job_interrupted_by_restart`. It does not replay work that may already have called an external provider or partially persisted a run.
- `/api/health` reports the number reconciled during this process start, and the UI renders an accessible safe-retry notice when the count is nonzero.
- The shell continues observing the read-only health contract after Hindsight first reports ready: visible tabs use a 30-second ready interval and the existing two-second starting/unavailable interval. Hidden tabs cancel the timer and perform one immediate reconciliation when visible again. Health observation never creates a review job or starts provider work.
- Each successful health response advances a localized semantic `time` beside the Hindsight indicator; failed reads preserve the prior successful check time. The timestamp is outside the dependency state live region, preventing unchanged 30-second observations from producing repeated assistive-technology announcements.
- Application-health request failure is tracked independently from the last successful payload: it displays `Memory status unknown`, forces the effective dependency gate unavailable, and preserves cached observation context. A successful response that reports unavailable Hindsight remains `Memory unavailable`, so operators can distinguish app/API reachability from dependency state without enabling memory work in either case.
- Application-health payload validation is equally fail closed: the response must be an object with exact healthy app status, configured/unconfigured memory state, starting/ready/unavailable Hindsight state, and a non-negative safe-integer interrupted-job count. Unconfigured memory cannot claim a starting or ready runtime. Invalid/partial responses follow the read-failure path, never advance the trusted check time, never open the memory gate, and never render an interrupted-job count.
- Consecutive application-health request failures retry after 2/4/8/16/30 seconds and stay capped at 30 seconds. A successful response resets the sequence. Visibility restoration bypasses a pending delay for one immediate check, preserving fast operator recovery without provider work.
- `Check health again` appears only while application health is unknown. It cancels pending backoff, reuses the observer's single-flight guard, disables duplicate activation while pending, and restores focus to the dependency status after either outcome. It remains a `GET /api/health` read and never creates provider work.
- Each application-health GET is aborted after 10 seconds. Timeout follows the same unknown/backoff path, releases the observer and manual control, preserves the last successful payload/time, and never becomes a confirmed Hindsight-unavailable response. Unmount aborts an outstanding health request.
